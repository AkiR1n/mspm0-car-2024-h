# ML Worktree Context

## 为什么单独开这个 worktree

这个目录对应分支 `ml-data-driven-car`，用途不是继续微调当前规则控制主线，而是开始尝试基于数据采集、建模和部署的小车控制方案。

建议把这个 worktree 当成一个新的工程目录使用：

- 在 VS Code 里单独打开 `/home/aki/workspace_ccstheia/mspm0-school-2026-ml`
- 不要和主线目录混开一个 workspace
- Codex / 其他代理会话也在这个目录重新开始

原因：

- ML 版本和当前规则控制版本后续差异会越来越大
- 数据集、训练脚本、推理代码、日志协议会引入新的目录结构
- 继续复用主线会话，容易把“当前稳定车”和“ML 实验车”混成一套上下文

### 与 ML 方向无关、先不处理的内容

下面这些属于规则控制主线继续优化的工作，不是这个分支的第一优先级：

- 继续手调 `Q4` 的圆弧循迹抖动
- 继续细调 `AC / BD` 偏置
- 继续围绕现有状态机做时间压榨
- 继续修改 OLED / 按键 / 声光这类现场操作细节

ML 分支不是为了把这些规则继续堆复杂，而是为了验证“数据驱动控制能否形成替代方案或增强方案”。

## 这个 ML 分支要做什么

目标不是直接把现有规则控制全部推翻，而是分阶段建立以下能力：

1. 先把数据采集链路做对
2. 再把离线分析和训练流程做通
3. 最后才讨论在线推理是否值得上车

建议的阶段目标如下。

### 阶段 1：数据采集

优先建立稳定、可重复的数据记录机制，至少覆盖：

- 时间戳
- 题目 / 圈数 / 相位
- 7 路循迹传感器原始值或位图
- `line_position`
- `yaw / gyro_z`
- 左右轮目标速度
- 左右轮实测速度
- `v / w`
- 编码器距离
- 关键事件标记（起跑、过点、出弯、停车）

这一阶段的产出应该是：

- 统一日志格式
- 采集脚本
- 数据集目录约定
- 至少一批可复现的 Q4 数据

### 阶段 2：离线分析

离线阶段先回答问题，再决定要不要上模型：

- 现有规则控制在哪些工况下最不稳定
- 圆弧段摇摆来自传感器噪声、控制输出突变，还是轨迹目标本身不连续
- 不同相位是否应该建不同模型或不同标签
- 哪些观测量对下一时刻 `w` 或左右轮修正最有用

这一阶段的目标不是“训练一个深模型”，而是先建立数据理解。

### 阶段 3：建模尝试

优先尝试小模型、可解释模型、可部署模型，例如：

- 线性回归 / 岭回归
- 小型 MLP
- 简单时序窗口模型
- 分类模型（相位 / 动作建议）

先验证以下问题：

- 模型是否比现有规则在某一类工况下更稳
- 模型是否只适合作为规则控制的修正项
- 推理耗时、内存占用、参数规模是否适合 MSPM0G3507

### 阶段 4：上车集成

如果模型离线效果成立，再考虑：

- PC 侧回放验证
- 固件内推理接口
- 模型参数导出格式
- 降级策略：模型失效时回退到规则控制

这里的原则是：**ML 是增强，不是先把主线拆掉再说。**

## 建议的工程边界

这个分支里，优先新增而不是直接侵入主线控制代码：

- `tools/collect/`：采集脚本
- `tools/replay/`：日志回放和可视化
- `ml/`：训练、评估、导出
- `datasets/`：数据集说明，不提交原始大数据
- `docs/`：实验记录和结论

建议 `.gitignore` 明确排除：

- `logs/`
- `datasets/raw/`
- `datasets/processed/`
- `checkpoints/`
- `runs/`
- `artifacts/`

原则：

- 代码和流程进 git
- 大体量数据、模型权重、临时产物不进 git

如果在这个 worktree 里重新开 Codex，会话开头建议直接说明下面这些信息：

> 这是 `ml-data-driven-car` worktree，不是当前稳定比赛主线。这里的目标是为小车建立数据采集、离线分析、模型训练和可能的部署流程，尽量不要直接把主线规则控制继续改复杂。

### 建议说明 2：当前主线能力

> 当前主线基于规则控制，Q1~Q4 已实测可完成，Q4 约 55s。主线继续负责稳定比赛版本；这个分支主要做 ML 实验，不默认去动主线现成状态机。

> 先帮助建立日志格式、采集工具、数据目录、离线分析脚本，再讨论模型选择和部署，不要一上来就写训练网络。

### 建议说明 4：工程约束

> 原始数据、训练产物、模型权重默认不要进 git；需要时优先单独分目录、单独脚本、单独文档，保持和主线边界清楚。

## 一句话结论

这个 worktree 的任务不是“继续把现有规则调到更极限”，而是“建立一条数据驱动控制的完整实验链路，并验证它值不值得上车”。
