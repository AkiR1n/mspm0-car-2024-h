  四、通信协议（K230 ↔ MSPM0）

  锁定以下格式，校赛起就用这一套，到省赛不再改：

  UART @ 115200-8N1
  0xAA 0x55 | FRAME_ID(1) | X_H X_L(2) | Y_H Y_L(2) | CONF(1) | XOR(1) | 0xFF
                                                                 前 7B 异或
  - 坐标：图像中心为原点，归一化 [-1, +1]，scale = 10000，传 int16
  - FRAME_ID = 0x01 有效 / 0x02 丢失
  - 100 ms 心跳；连续 3 帧丢失 → MSPM0 进入"搜索模式"
  - MCU 端用 UART + DMA + 环形缓冲，帧解析状态机写死在中断尾

  同步原语：
  - K230 UART：DMA + 空闲中断 → xTaskNotifyGiveFromISR 唤醒 k230_rx_task
  - I²C（MPU6050/OLED 共享）：互斥量 保护

   带值（比队列轻）

  抖动不可接受，改用 TIMG 硬件中断直接跑 PID（任务只做设点/读数）

  M0+ 中断优先级坑：
  - Cortex-M0+ 只有 2 位优先级（4 级，0–3，数字越大优先级越低）
  - FreeRTOS CM0 端口要求 PendSV/SysTick 在最低优先级（= 3）
  - 任何调用 ...FromISR() 的外设中断优先级必须同样配置在 M0+ 允许 RTOS
  感知的范围内
  - 注意 configKERNEL_INTERRUPT_PRIORITY = 0（模板里的值）在 CM0 端口语义与
  CM3/4 不同，首周跑起来后用 configASSERT + 
  栈溢出检查（configCHECK_FOR_STACK_OVERFLOW = 2）做实际验证

  │ 通用）     │ 的管理逻辑       │  / queue.c / list.c / │ 永远不改       │
  │            │                  │  timers.c ...）       │                │
  ├────────────┼──────────────────┼───────────────────────┼────────────────┤
  │            │ 上下文切换、SysT │                       │                │
  │ ②Port（架  │ ick 处理、NVIC   │ FreeRTOS/portable/GCC │ 永远不改，但要 │
  │ 构相关）   │ 操作，由汇编/CMS │ /ARM_CM0/             │ 选对端口       │
  │            │ IS 实现          │                       │                │
  ├────────────┼──────────────────┼───────────────────────┼────────────────┤
  │ ③Heap      │ pvPortMalloc     │ FreeRTOS/portable/Mem │ 选型 + 调 size │

  MSPM0G3507 是 Cortex-M0+，所以端口是 ARM_CM0（FreeRTOS 11.x 把 Cortex-M0/M0+

  三、Cortex-M 芯片跑 FreeRTOS 离不开的三个异常

  这是理解为什么移植"需要动底层"的关键。

  ┌─────────┬────────────────────────────────────────┬───────────────────────┐
  │  异常   │                  负责                  │       是谁触发        │
  ├─────────┼────────────────────────────────────────┼───────────────────────┤
  │         │ RTOS 的时基（默认 1 ms）。触发后调     │ 内核的 SysTick        │
  │ SysTick │ xPortSysTickHandler 让 tick 加 1 +     │ 定时器，由            │
  │         │ 唤醒因 vTaskDelay 沉睡的任务           │ xPortStartScheduler() │
  │         │                                        │  启动                 │
  ├─────────┼────────────────────────────────────────┼───────────────────────┤
  │         │ 实际的上下文切换（保存当前任务寄存器 → │ 需要切换时由 port.c   │
  │ PendSV  │  切栈 → 恢复下一个任务）               │ 写 ICSR.PENDSVSET     │
  │         │                                        │ 触发                  │
  ├─────────┼────────────────────────────────────────┼───────────────────────┤
  │ SVC     │ 启动第一个任务（因为此时栈指针还没切） │ vTaskStartScheduler() │
  │         │                                        │  内部执行 SVC #0 一次 │
  └─────────┴────────────────────────────────────────┴───────────────────────┘

  移植最容易踩的第一个坑：SysTick 是 Cortex-M 核心的资源，裸机代码和 FreeRTOS
  都想用。谁都要，但必须由 FreeRTOS 独占。这就是我们在 Phase 3 删掉 car-25 的
  SysTick_Init + SysTick_Handler 的原因——FreeRTOS/portable/GCC/ARM_CM0/port.c
  已经在 xPortStartScheduler() 里配好了。

  // ❌ 裸机时代的 car-25 clock.c — 与 FreeRTOS 冲突
  void SysTick_Handler(void) { tick_ms++; }
  void SysTick_Init(void) { DL_SYSTICK_config(CPUCLK_FREQ/1000); }

  // ✅ FreeRTOS 下直接扔掉，tick 从内核拿
  #define tick_ms  ((unsigned long)(xTaskGetTickCount() * portTICK_PERIOD_MS))

  PendSV/SVC 在 M0+ 上优先级必须是最低（值最大），否则抢占中断链路会乱。FreeRTOS
   的 CM0 port 内部自己设好了，不用管。

  四、模板到底在做什么 — 5 处关键配置

  把 SDK 例程改成 FreeRTOS 应用，需要改动的点都在模板里：

  ① FreeRTOSConfig.h — RTOS 的 BIOS

  ▎ Includes/FreeRTOSConfig.h

  MCLK 一致
  #define configTICK_RATE_HZ            1000         // tick 周期 1 ms
  #define configUSE_PREEMPTION          1            // 抢占调度
  #define configMAX_PRIORITIES          8            // 任务优先级数
  #define configMINIMAL_STACK_SIZE      128          // 最小任务栈 (words)
  #define configTOTAL_HEAP_SIZE         (1024*16)    // heap_4 的池，我们设 16 
  KB
  #define configCHECK_FOR_STACK_OVERFLOW 2           // 开栈溢出检查（调试用）
  #define configENABLE_MPU              0            // M0+ 没 MPU
  #define configENABLE_FPU              0            // M0+ 没 FPU

  最容易错的就是 configCPU_CLOCK_HZ：它告诉 port.c 去算 SysTick 的 reload 值 =
  CPU_CLOCK_HZ / configTICK_RATE_HZ。如果 SysConfig 里实际 MCLK 是 32 MHz 但
  FreeRTOSConfig 写的是 80 MHz，那每次 vTaskDelay(1000) 实际要等 2.5 s。

  我们项目里 SysConfig 的 PLL_PDIV=2、PLL_QDIV=5、HSCLKMUX=SYSPLL2X→ 80
  MHz，刚好对齐。

  SysTick_Handler、PendSV_Handler、SVC_Handler。它们都是弱符号，port.c
  里用同名函数覆盖：

  ELF，链接器就会把弱符号覆盖掉。这也是为什么我们在 CMakeLists 里要写：
  file(GLOB_RECURSE FREERTOS_PORTABLE_C_SOURCES
  "./FreeRTOS/portable/GCC/ARM_CM0/*.c")

  ③ Heap — 选 heap_4

  file(GLOB FREERTOS_MEMMANG_C_SOURCES "./FreeRTOS/portable/MemMang/heap_4.c")

  FreeRTOS 提供五个 heap 实现：

  ┌────────┬────────────────────┬────────────────────────┐
  │  heap  │        特点        │       什么时候选       │
  ├────────┼────────────────────┼────────────────────────┤
  │ heap_1 │ 只分配不释放       │ 永不释放的系统         │
  ├────────┼────────────────────┼────────────────────────┤
  │ heap_2 │ 有释放但不合并碎片 │ 碎片可接受的旧系统     │
  ├────────┼────────────────────┼────────────────────────┤
  │ heap_3 │ 包装 newlib malloc │ 要跟 printf 共享堆     │
  ├────────┼────────────────────┼────────────────────────┤
  │ heap_4 │ 释放 + 合并相邻块  │ 默认首选，绝大多数项目 │
  ├────────┼────────────────────┼────────────────────────┤
  │ heap_5 │ 跨多段 RAM         │ RAM 分段的大芯片       │
  └────────┴────────────────────┴────────────────────────┘

  选 heap_4 后，xTaskCreate、xQueueCreate 等动态分配都走这个 16 KB 池，不要和
  newlib malloc（sysmem.c 里的 _sbrk）混着用。

  ④ 重写 main() — 核心心智转换

  裸机和 RTOS 最大的区别就在这里：

  // ── 裸机 ──
  int main(void) {
      SYSCFG_DL_init();
      external_init();
      while (1) {
          task1_step();
          task2_step();
          delay_cycles(N);          // 死等
      }
  }

  // ── FreeRTOS ──
  int main(void) {
      SYSCFG_DL_init();              // ★ 只做硬件底层初始化
      // 其他外设初始化搬到任务体内

      xTaskCreate(task1, "t1", 512, NULL, 5, NULL);
      xTaskCreate(task2, "t2", 512, NULL, 4, NULL);

      vTaskStartScheduler();         // ★ 不再返回，由 SysTick+PendSV 轮转
      for (;;);                      // 调度器启动失败才会跑到这
  }

  void task1(void *arg) {
      sensor_init();                 // ★ 放在任务里，因为可能含 vTaskDelay
      for (;;) {
          do_work();
          vTaskDelay(pdMS_TO_TICKS(10));   // ★ 不耗 CPU 的延时
      }
  }

  关键认知转换：
  - main() 只管创建任务，不"跑"任何业务逻辑
  - 每个任务是独立的 while(1)，一定要 vTaskDelay
  或阻塞在某个事件上，否则低优先级任务永远拿不到 CPU
  - 任何阻塞的外设初始化（DMP 初始化里的几百毫秒延时）必须放任务体里，不能放
  main() 的 vTaskStartScheduler() 之前——那时 SysTick 还没跑，vTaskDelay 会死等

  ⑤ CMake 链接顺序（我们刚踩过的坑）

  # ❌ 错：库放 add_link_options（在对象文件之前）
  add_link_options(-lm -lnosys)
  add_executable(...)

  # ✅ 对：库放 target_link_libraries（在对象文件之后）
  add_executable(...)
  target_link_libraries(... PRIVATE
      -Wl,--start-group  m c nosys gcc  -Wl,--end-group)

  原因：静态库按需加载。链接器扫描对象文件看到 atan2f 未定义时，必须之后才扫
  libm.a。如果 -lm 在对象前面，linker 过 libm.a 时没看到需求就跳过，对象里的
  atan2f 就永远 undefined。

  五、一个最小可跑的 FreeRTOS 例程（等价替换 SDK gpio_toggle）

  如果把 SDK 的 gpio_toggle_output.c 改写成 FreeRTOS 版：

  // 新 main.c（对比裸机版的 SDK 例程）
  #include "ti_msp_dl_config.h"
  #include "FreeRTOS.h"
  #include "task.h"

  static void led_task(void *arg) {
      (void)arg;
      for (;;) {
          DL_GPIO_togglePins(GPIO_LED_PIN_1_PORT, GPIO_LED_PIN_1_PIN);
          vTaskDelay(pdMS_TO_TICKS(500));      // 取代 delay_cycles(16000000)
      }
  }

  int main(void) {
      SYSCFG_DL_init();
      xTaskCreate(led_task, "led", 128, NULL, 1, NULL);
      vTaskStartScheduler();
      for (;;);
  }

  跑起来现象和裸机一样：LED 1 Hz 闪。但 CPU 其余时间在 idle task
  里，如果加第二个任务它可以同时响应串口 / 读 sensor，这就是 RTOS 的价值。

  六、移植时最容易踩的 6 个坑

  1. configCPU_CLOCK_HZ 和 SysConfig MCLK 不一致 → vTaskDelay 实际时间错
  2. SysTick 冲突 → 同时存在两个 SysTick_Handler，链接器可能抱怨或把 tick 打飞
  3. PendSV/SVC 优先级不对 → 很少见（port.c 设好了），但如果有人手动
  NVIC_SetPriority(PendSV_IRQn, 0) 就翻车
  4. 在调度器启动前 vTaskDelay → 永远卡死，因为 SysTick 还没走
  5. 没开栈溢出检查 → 任务栈不够时静默
  hardfault，找半天；configCHECK_FOR_STACK_OVERFLOW = 2 +
  vApplicationStackOverflowHook 能直接定位到哪个任务
  6. 链接顺序错导致 atan2f / newlib syscall 找不到 → 用 target_link_libraries
  而非 add_link_options 放库

● 记对了——CubeMX 里 System Core → SYS → Timebase Source 下拉，默认 SysTick
  可以改成任何 TIM（常见选 TIM6/TIM7/TIM17）。这是 STM32 HAL 独有的配置项，MSPM0
   没有。

  为什么 STM32 需要这么做

  STM32 HAL 架构里有两个互相独立的 tick：

  ┌───────────────────────────┬────────────────────────┬───────────────────┐
  │            谁             │         干什么         │      默认源       │
  ├───────────────────────────┼────────────────────────┼───────────────────┤
  │ HAL（HAL_Delay,           │ 驱动 HAL 内部          │ SysTick，每 1 ms  │
  │ HAL_GetTick）             │ timeout、HAL_Delay     │ 调 HAL_IncTick()  │
  │                           │ 忙等                   │                   │
  ├───────────────────────────┼────────────────────────┼───────────────────┤
  │ FreeRTOS（vTaskDelay,     │ 调度器时基             │ SysTick           │
  │ xTaskGetTickCount）       │                        │                   │
  └───────────────────────────┴────────────────────────┴───────────────────┘

  两个都抢 SysTick_Handler → 冲突。CubeMX 在勾选 FreeRTOS 时会弹红框警告并建议改
   HAL Timebase，通常选：
  - TIM6 / TIM7（基本定时器，专门干这个活最合适）
  - TIM17（蓝桥杯板子常用，因为 G431 的基本定时器不多 + 这个 TIM
  其它地方不易冲突）

  改完之后：
  - FreeRTOS 独占 SysTick → PendSV/SVC/SysTick 三位一体正常
  - HAL 用 TIM17 → CubeMX 自动生成 TIM17_IRQHandler → HAL_IncTick()，周期 1 kHz

  CubeMX 背后生成的代码大致是：

  // stm32g4xx_hal_timebase_tim.c（自动生成）
  void TIM17_IRQHandler(void) { HAL_TIM_IRQHandler(&htim17); }
  void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim) {
      if (htim->Instance == TIM17) HAL_IncTick();
  }
  HAL_StatusTypeDef HAL_InitTick(uint32_t TickPriority) {
      // 配 TIM17 1 ms 中断，替代默认的 SysTick
  }

  MSPM0 为什么不用做这件事

  因为 MSPM0 driverlib 根本没有"全局 HAL tick"的概念。

  ┌───────────┬───────────────────────────────────────┬─────────────────────┐
  │   框架    │            有没有自带 tick            │ FreeRTOS 下如何共存 │
  ├───────────┼───────────────────────────────────────┼─────────────────────┤
  │ STM32 HAL │ 有（HAL_GetTick）                     │ 必须把 HAL 时基改到 │
  │           │                                       │  TIM                │
  ├───────────┼───────────────────────────────────────┼─────────────────────┤
  │ Renesas   │ 有（R_BSP_SoftwareDelay，但不基于全局 │ 不需要改，FSP       │
  │ FSP       │  tick）                               │ 的延时是忙等        │
  ├───────────┼───────────────────────────────────────┼─────────────────────┤
  │ MSPM0     │ 无                                    │ 不需要改，FreeRTOS  │
  │ driverlib │                                       │ 直接拿 SysTick      │
  ├───────────┼───────────────────────────────────────┼─────────────────────┤
  │ GD32 HAL  │ 有（仿 STM32 HAL）                    │ 同 STM32，要改 TIM  │
  └───────────┴───────────────────────────────────────┴─────────────────────┘

  所以我们的 mspm0-car-2026 里没有这一步。删掉 car-25 原作者自己写的
  SysTick_Init 后，SysTick 就完全空出来给 FreeRTOS 了，不需要再挪到 TIM6/TIM17。

❯ 那driver是怎么改造的呢                                                        

● DriverLib 的时基哲学

  DriverLib 和 HAL 走的是完全相反的路线。

  一、DriverLib 不"自带 tick"，它只是寄存器包装

  DriverLib 里每个 DL_* 函数几乎都是 1-3 行寄存器读写：

  // dl_gpio.c 节选（SDK 源码）
  __STATIC_INLINE void DL_GPIO_togglePins(GPIO_Regs *gpio, uint32_t pins) {
      gpio->DOUTTGL31_0 = pins;           // 就这一句
  }

  __STATIC_INLINE bool DL_I2C_isControllerRXFIFOEmpty(I2C_Regs *i2c) {
      return ((i2c->MASTER.MSR & I2C_MSR_RXFE_MASK) == I2C_MSR_RXFE_SET);
  }

  没有全局状态、没有内部计时器、没有 HAL_Lock 
  这种东西。这意味着它不抢任何系统资源。

  二、那怎么做"毫秒延时"和"超时"？

  DriverLib 留给调用方自己处理。有两个工具箱：

  ① 纯 CPU 周期延时 — delay_cycles(N)

  SDK 提供的 delay_cycles 是 ASM 忙等循环，按 CPU cycle 计数，不依赖 SysTick：

  // 在 ti/devices/msp/peripherals/hw_hal.h
  __STATIC_INLINE void delay_cycles(uint32_t cycles) {
      // 用 ASM 精确消耗 N 个 cycle（不调度，不让出 CPU）
  }

  这是裸机版 MSPM0 例程里唯一的"延时"机制——SDK 的 gpio_toggle 就在用它：
  delay_cycles(16000000);   // 80 MHz 下约 200 ms

  ② 毫秒级延时 / 超时 — 应用自己写

  DriverLib 不提供"等 100 ms"这种函数。应用代码按场景自己实现：

  裸机写法（car-25 最早的样子）：
  // Drivers/MSPM0/clock.c —— car-25 自己造的轮子
  volatile unsigned long tick_ms;
  void SysTick_Handler(void) { tick_ms++; }           // 自己用 SysTick

  int mspm0_delay_ms(unsigned long num_ms) {
      unsigned long start = tick_ms;
      while (tick_ms - start < num_ms);                // 忙等，不让 CPU
      return 0;
  }

  FreeRTOS 改造后（我们 Phase 3 做的）：
  // Drivers/MSPM0/clock.c —— FreeRTOS 版
  #include "FreeRTOS.h"
  #include "task.h"

  int mspm0_delay_ms(unsigned long num_ms) {
      vTaskDelay(pdMS_TO_TICKS(num_ms));               // 让出 CPU
      return 0;
  }
  #define tick_ms  ((unsigned long)(xTaskGetTickCount() * portTICK_PERIOD_MS))

  关键点：mspm0_i2c.c 里 I²C 驱动调用 mspm0_delay_ms 和
  mspm0_get_clock_ms，这两个函数的名字、签名、返回值完全没动——I²C
  驱动代码一行也没改，就从"SysTick 忙等"无缝切到了"FreeRTOS 让出"。这就是
  DriverLib 能跨 RTOS 迁移的根本原因：延时被隔离在应用层的一个文件里。

  三、三家 HAL 风格对比

  看同一件事"I²C 读 10 字节，100 ms 超时"：

  STM32 HAL — 包办式

  HAL_I2C_Master_Receive(&hi2c1, 0xD0, buf, 10, 100);   // 100 = timeout_ms
  // HAL 内部调用 HAL_GetTick() 循环比对，自己判断超时
  // 它读哪个 tick？—— 取决于 Timebase Source 配置
  //   默认：SysTick
  //   若改到 TIM17：TIM17_IRQHandler 里 HAL_IncTick

  HAL 绑定在某个 tick 源上，所以和 FreeRTOS 抢 SysTick 时必须挪到 TIM17。

  Renesas FSP — 事件驱动 + 回调

  R_IIC_MASTER_Read(&g_i2c0_ctrl, buf, 10, false);
  // 不阻塞，直接返回
  // 等 callback（i2c_callback）被触发报 EVENT_RX_COMPLETE
  // 超时是外层应用自己计时（R_BSP_SoftwareDelay 或 RTOS 延时）

  FSP 内部没有全局 tick 依赖（它的 R_BSP_SoftwareDelay 是 cycle 忙等），所以跟
  FreeRTOS 天然不冲突。

  TI DriverLib — 纯寄存器 + 应用层包超时

  // 应用自己写（见 car-25 的 mspm0_i2c.c）
  int mspm0_i2c_read(u8 addr, u8 reg, u8 len, u8 *data) {
      unsigned long start, cur;
      mspm0_get_clock_ms(&start);                     // ← 唯一的 tick 接触点
      DL_I2C_startControllerTransfer(...);
      do {
          if (!DL_I2C_isControllerRXFIFOEmpty(...))
              data[i++] = DL_I2C_receiveControllerData(...);
          mspm0_get_clock_ms(&cur);
          if (cur >= start + I2C_TIMEOUT_MS) {        // 应用层判超时
              return -1;
          }
      } while (!DL_I2C_getRawInterruptStatus(..., RX_DONE));
      return 0;
  }

  整个 driverlib 层完全不碰 tick，只有应用包装（mspm0_i2c.c）在接触。换 RTOS
  时只要改这一个文件里的两行 (mspm0_get_clock_ms + mspm0_delay_ms)。

  五、实际改造步骤（回你具体问的问题）

  car-25 移植 driverlib 到我们 FreeRTOS 工程时，driverlib 本身零修改。变的只有：

  1. Drivers/MSPM0/clock.c — 把 mspm0_delay_ms 底层从"SysTick + tick_ms
  忙等"换成 vTaskDelay；把 mspm0_get_clock_ms 从"读 tick_ms"换成
  xTaskGetTickCount() * portTICK_PERIOD_MS。2 个函数，各 1 行。
  2. Drivers/MSPM0/interrupt.c — 删掉车主自己加的 SysTick_Handler（和 FreeRTOS

  关键设计原则

  1. 参数/状态分离：所有 *_config_t 可用 const 静态表，便于整定和跨任务共享
  2. 纯函数化：turn_detection_update(now_ms) 不读全局时间，可离线单元测试
  3. 依赖注入：motion_control 不再 extern float yaw，解耦 MPU6050
  4. 显式 dt：PID / motion step 都接收 dt 参数，不隐式假定 10 ms
  5. 不在 init 启 HW 定时器：所有 *_init 只做状态清零 +
  NVIC，计时器启动留给调用方（任务化架构必需）
  6. ISR 钩子明确命名：encoder_on_gpio_irq / encoder_on_tick_irq 清楚表达被上层

  发现的 bug

  我们在 Phase 3 删了 v1 的 TIMA1_IRQHandler（因为 PID 搬到了任务），但

  DL_TimerA_startCounter(TIMER_CALC_INST);

  而我们的新 interrupt.c 没有定义 TIMA1_IRQHandler → 中断来了会进 MSPM0 startup
  的 Default_Handler（一个死循环）。板子跑起来约 10 ms 后就卡死。

  里驱动的，pid_task 调 Encoder_GetSpeed_PPS 依赖它。

  修复：在 interrupt.c 加回 TIMA1_IRQHandler，但职责仅做速度计算（不碰 PID，PID
  仍在任务里跑）。
